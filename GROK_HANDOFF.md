# Prompt for Grok: make VISION Community operational

You are continuing a partially built, standalone VISION Community project. The owner wants a real public site, not merely the synthetic local demo. Work autonomously, inspect and test what is already here, and keep the owner informed of concrete progress and constraints. Do not edit the existing VISION project, the MMA fork, or any other reference repository. Create a new **private** GitHub repository for this project when the code is ready; keep all public site branding, commit metadata, source maps, logs, and account identifiers free of the owner's personal identity.

## Nonnegotiable product requirements

- Every accepted scene location earns 1 unit. Every accepted object location earns 10 units. **Each search costs exactly 100,000 units.** New accounts start with 0 units and 0 searches; there are no trial, owner, UI, API, or admin bypasses. Thus one search requires 100,000 verified scene locations, 10,000 verified object locations, or an equivalent mix. Credit only after verified work is durably published. Debit atomically before revealing or executing a new search. Idempotent retries must not grant or spend twice.
- The owner and all users search the **same** verified, cumulative index. Work assigned to one user must not be assigned simultaneously to another. Deduplicate canonical source asset/capture/lane/model identities and honor the current VISION pipeline's relevant spatial duplicate rules. Expired leases may be reassigned; stale submissions cannot publish or earn credit.
- Users pay nothing, provide no Google/API credentials, and should have a simple browser flow. The owner does not want to use personal API keys or pay for Google/API inference. Slow, medium, and max must control actual processing resource use, not merely an animation.
- The desired recurring owner expense is only R2 storage, preferably under $20/month. Use free tiers while building. Do not activate a paid plan, add a payment method, incur charges, or reserve large storage without explicit owner approval. Create the R2 bucket **last**, after code, tests, a measured storage/operation budget, and a deployment plan are ready. The other AI has access to the owner's GitHub and Cloudflare accounts for the new repo and final free-tier setup.
- Nothing in the public application may identify the owner. Avoid analytics, user names/emails unless truly needed, query logging, private MMA identifiers, and location-sensitive account data. Use secure anonymous sessions and a recovery approach that does not undermine privacy.

## Source and architecture constraints

Use the existing VISION architecture as the design reference, read-only. `../VISION/README.md`, `VisionEngine.swift`, the scene sidecar/registry, and `object-sidecar` describe checksummed 500,000-location sealed scene segments with atomic registry publication and a separate Gen4 object index with versioned manifests, six-face processing, RF-DETR, YOLOE, and OWLv2/PQ128. Preserve the useful format/version/checksum/atomic-publication ideas and search semantics. Port only what is lawful and technically appropriate to this **new** project. Do not alter the local VISION or MMA code, process supervisors, production databases, or indexes. Do not copy private MMA profile data or current index artifacts to public storage.

The current VISION corpus derives from Google Street View and uses Google endpoints. Google's published Street View policy generally prohibits prefetching, indexing, storing, or caching imagery, and standard Maps terms prohibit bulk extraction and derived indexes. **Do not wire any Google imagery, undocumented Google endpoint, existing Google-derived index, or personal Google API into the public app unless the owner produces written rights covering the exact proposed use.** Ask once for that evidence if needed. Otherwise choose a genuinely rights-cleared imagery source and preserve its license/attribution. If no suitable source exists without violating the no-API/no-cost constraints, implement the source interface and stop before real ingestion; explain the blocker plainly.

The existing `community/` package is an intentionally synthetic prototype: Python/SQLite queue and credit ledger, canonical deduplication, expiring exclusive leases, publication into one shared index, server-side search gate, HTTP-only anonymous cookie, local page, and an audit/backup CLI. `community/demo_catalog.json` has only invented records; `fixture_output` is trivially forgeable and the label search is not VISION search. The local server binds to loopback. Treat its tests and behavior as a starting contract, not a public deployment. The repo has no remote yet. `README.md`, `PRODUCTION_PLAN.md`, and `COST_FEASIBILITY.md` document the current state.

## Critical feasibility test before choosing hosting

Prove or disprove the owner's simultaneous requirements: only R2 storage expense, fast search over the intended corpus, free user-side processing, and a search gate that cannot be gamed. A client cannot prove it actually ran an expensive model merely by returning a hash; independent trusted recomputation or a sound proof is required for a true guarantee. Sending index shards to the browser can allow unlimited offline searches after one authorized request. A server-side search/verification system consumes compute, bandwidth, database operations, and often paid hosting. Never label sampling or browser code “absolute” enforcement. Present an honest cost/security tradeoff and the smallest relaxation required if the combination cannot be achieved.

Verify current official Cloudflare limits and model costs. As of September 2026, R2 Standard lists 10 GB-month storage free, then $0.015/GB-month plus request charges; Workers Free lists 100,000 requests/day, 10 ms CPU/request, and 128 MB memory; D1 Free lists 5 GB total and daily row limits; Vectorize Free lists only 5 million stored dimensions. These limits may be unsuitable for VISION-scale ranked search. The existing sealed scene segment directory is roughly 20 GB locally, while the entire local VISION Application Support directory is roughly 75 GB. These are rough local measurements, **not** permission to upload them and not a complete future object/image footprint. Measure bytes per index entry, model asset size, R2 operations, worker downloads, query CPU/memory, database row volume, and projected searches before promising a monthly cost. Keep raw imagery and derived index costs separate.

## Implementation and acceptance

1. Audit the current standalone code and repair any security, consistency, and usability defects. Make an explicit architecture decision for a source importer, browser/native processing worker, trusted verification, durable queue/ledger, immutable R2 segments, shared search backend, and backups. Prefer staged releases and measurable benchmarks.
2. Build a rights-aware import contract and canonical job identity; implement exclusive leases with expiry/fencing; reject duplicate or stale outputs. Add versioned model/output manifests and independent output verification. Publish only verified segments to the common registry. Port the existing scene/object search formats or build a parity-tested adapter; avoid replacing visual search with metadata/label matching in the real service.
3. Enforce credits entirely in trusted server code. Verify no search path, cache, alternate endpoint, direct R2 access, replay, concurrent request, account recreation, or owner role can reveal results without sufficient verified units. Use scoped R2 credentials only on the server, never in browser code. Keep the full searchable index inaccessible to clients.
4. Make the UI usable across current browsers, with honest progress, real slow/medium/max resource limits, pause/resume, privacy-friendly anonymous account recovery, and clear accounting. Test multiple users contributing to and searching one index.
5. Add meaningful concurrency, fraud, recovery, and end-to-end tests. Benchmark at realistic scale. Run the audit/backup command and restore a backup. Document failure modes and remaining risks.
6. Create the new private GitHub repo for **this** project. Deploy only components that fit the free tier and the owner-approved data rights. Defer R2 bucket creation until the final integration step. Do not publish a real searchable corpus or claim the site is operational until the source rights, verification, search parity, and cost gates pass.

If you cannot finish a gate, continue all independent work, leave a concrete reviewable artifact, and report precisely what is blocked, what decision is needed, and the next command/action. Never substitute a synthetic demo for the requested public VISION service without labeling it as such.
