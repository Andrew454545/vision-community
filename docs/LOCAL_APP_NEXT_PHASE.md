# Next phase: a free local VISION application

The next phase uses the owner's VISION workflow as the product reference: a local
library, text/image search, useful metadata filters and MMA connections. Users
search what their own computer has indexed. There is no central paid search,
credit economy or service account in this path.

## Current full-app implementation

The owner has now asked to keep building the full local application. Photo search
is implemented in source after the published a3402cb preview: private local pixels,
photo/text blending and native ranking passed one actual offline synthetic use.
Serial downloads/group pauses and owned bounded recovery are also implemented
in source. Personal MMA-map import/private queues are now implemented too,
including saved-reference admission, cross-map reservation recovery, separate
personal result storage and combined local search. Next: local Objects and a complete
app shell. Existing operational holds still
apply. See the library guide for exact photo-query scope and private scratch limits.

## Delivery order

**16 October progress:** the invited path includes the local library/text search,
metadata filters, Street View/MMA-JSON references, selectable storage, optional
memory-only online MMA export, assignment-checked owner import and additive
owner-catalog preparation/apply. See [library/import details](LOCAL_SCENE_LIBRARY.md).
The owner's Google requests remain paused. Current CPU speed settings are not a
per-request network rate limit; serial downloads and30-second group pauses are now
implemented without a live provider test. First-user Windows/live feedback, actual returned
work registration, local Objects and a complete app shell remain. Signed public downloads
need signing enrollment. No actual contributor output or personal VISION catalog
has been changed by the development checks.

1. **One local library with search.** Make completed Scene work appear in a Library
   tab automatically. Reuse the current native four-view index, models and ranker.
   Compact small completed packets into normal VISION segments by copying vector
   bytes, rather than recomputing embeddings. Add text search and reference-image
   search with result previews, country, panorama and map links. Start with one
   actual saved index and one useful search; broaden from early user feedback.
2. **Metadata, storage and everyday use.** Preserve original panorama/native source
   identities, heading, pitch, zoom, country and supported generation labels. Add
   the same useful filters as the owner's application. Unknown tags remain unknown
   until supported by source evidence; enrichment must not require re-indexing.
   Let users choose a local/external storage folder, see progress and remaining
   space, and keep the same day/night, battery, pause and recovery controls.
3. **Owner import and private sharing.** Add an owner-side import of portable
   contribution exports into a separate additive VISION segment. Check assignment,
   hashes, complete masks, metadata and duplicates before registering it; leave the
   existing owner indexes and reserved queue untouched. Start with private manual
   transfer. Then offer optional batched R2 sharing with limited upload authority,
   no bucket keys on contributor devices and no server inference/search. R2 is
   storage/transfer, not a per-location Worker/database processing loop.
4. **MMA and then Objects.** Connect the local MMA first through its existing local
   interface, with explicit map selection. Add the online MMA through the user's
   own authorized connection; keep those credentials local. Export selected search
   results back to MMA. Add cross-platform Object processing only after the Scene
   library and search are useful, with its own existing qualification evidence.

## What counts as finishing the first phase

The invited kit installs its own private Python/models, runs the fixed112 check,
returns a private report, obtains an owner-reviewed personal queue and saves local
indexes/portable exports. The owner can review the ZIP and prepare delivery with
one command. A first tiny live queue is ordinary first use, not another broad
calibration matrix. Then issue the long queue from the single private registry.

The current owner inventory has more than five million eligible rows prepared.
The owner's connection returned Google's automated-query HTTP403 refusal during
one finite live check. The client now stops on provider refusal/rate limiting,
instead of burning through the whole queue. A normal connection that is permitted
to retrieve imagery is an external requirement; frozen numerical checks cannot
promise it. Do not bypass provider refusals, change the gold pipeline to conceal a
failure, or label an unexecuted Windows path as tested.

## Fast implementation policy

Build a complete usable slice, then use it. Keep the existing numerical, duplicate
and privacy checks; do not repeat full model matrices or broad regression suites
for UI/delivery changes. One focused check for a changed boundary and one short
end-to-end use are enough unless a failure points to a specific additional check.
Treat the first invited installations as feedback, rather than adding a separate
clean-device/endurance project before anyone can begin. No Actions spending or
old cloud/native job restart follows from this plan. Unsigned invited previews
remain distinct from a signed public production release.
